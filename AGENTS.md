# yapa

How yapa is built and how to work on it. Goals and how they are measured are in GOALS.md; fium rules in ~/Documents/fium/RULES.md.

## Target
iPhone SE (1st gen, A9, arm64, not arm64e), iOS 15.8, jailbroken with Dopamine (rootless, semi-untethered).

- **Daemons** are Go binaries built by `./build-ios` into `build/ios` (Go links ios/arm64 only through cgo, so it uses Xcode's iPhoneOS SDK), signed with `ldid`, and run as launchd daemons from `/var/jb/usr/libexec/yapa/`. `yata` watches the services listed in `/var/jb/etc/yapa/services.json` and answers `/health` on port 8077, to the home network only. It also cuts the logs in `/var/jb/var/log/yapa` hourly: 5 MB each, 50 MB in all.
- **`./ya install root@<ip>`** sends the core (yata, Caddy, cloudflared, with their plists in `launchd/`) and every part over one ssh connection, unloads and reloads them. It needs root SSH by key. On rootless Dopamine root's home is `/var/jb/var/root`, so the key goes in `/var/jb/var/root/.ssh/authorized_keys`, not `/var/root/.ssh`. The plist needs no rootless changes: launchd loads it from `/var/jb/Library/LaunchDaemons/` (owned root:wheel) and runs the ldid-signed binary as is.
- **Parts** are everything else on the phone: `~/.config/yapa/parts/<name>/part` holds `key=value` lines (`name`, `kind` site or service, `run`, `port`, `check` in yata's format, `address`, `needs`, `mem`), and a `down` file beside it means installed but off. `./ya add site|service`, `./ya on|off` and `./ya parts` manage them. Each sync regenerates the phone's service plists, `services.json` and Caddyfile (from `phone/Caddyfile`) from the core and the parts that are on, so a part is watched by yata and its log, in `/var/jb/var/log/yapa`, is tidied with no extra step. `needs=` lists parts that must be on first. Commands reach the phone `./ya install` last used (`~/.config/yapa/host`); an address is a Caddy block plus a DNS name made with the Mac's `cloudflared tunnel route dns`, never the apex, www or the main site.
- **jeta**, the pad (shown on the phone as **miga**: its ants are crumbs, not faces), is a native app (Swift, UIKit, iOS 15), installed with TrollStore. It is a Claude Hardware Buddy: a CoreBluetooth peripheral on the Nordic UART Service, speaking newline-delimited JSON as specified in https://github.com/anthropics/claude-desktop-buddy/blob/main/REFERENCE.md. It advertises a name starting with `Claude`, requires encryption on its characteristics, and echoes `prompt.id` exactly in `{"cmd":"permission","id":…,"decision":"once"|"deny"}`. iOS advertises the name only while the app is in the foreground, so jeta stays in front.
- The protocol core (parsing, state, decisions) is a Swift package with no UIKit or CoreBluetooth imports, so `bench/jeta-buddy` runs it on the Mac.
- `jeta/` holds JetaKit (the face and ant models, no UIKit), BuddyKit (the Hardware Buddy protocol, no UIKit or CoreBluetooth) and `App/` (UIKit: the view that draws the ants, and the BLE link). `jeta/build-app sim` builds `build/jeta/sim/jeta.app` for the Simulator; `jeta/build-app device` builds `build/jeta/jeta.ipa` for TrollStore, and `jeta/install` puts it on the phone over SSH, restarts bluetoothd so the Claude desktop app reconnects by itself, and waits for heartbeats. The app logs the link to `Documents/buddy.log` on the phone. There is no Xcode project: swiftc compiles both straight from source. iOS 27 Simulators refuse apps without a scene delegate, so the app uses one.
- Claude's desktop app lists a device only if macOS's name for it starts with `Claude`, and for a phone that's the phone's own name, so the SE is named `Claude-yapa`. Its status ack must carry every `bat`, `sys` and `stats` field, and it sends `prompt` only for short, simple requests; other waiting prompts arrive as `waiting` alone.
- The screen shows one white ant per session (JetaKit's `Colony`, designed in `jeta/proto/ants`), each acting out its session's mood; the faces (`Face`, two small white ovals drawn from `Stroke.outline()`) are still the mood models behind them (blinks, moods, dozing off) but are never drawn. An ant has a real ant's shape: head, thorax, a small waist, an abdomen that trails like a rope, and six long, nearly straight legs from the thorax. Its legs follow RujiK's procedural salamanders: each foot stays planted until its step spot (half a stride ahead) is a stride away, then steps there, one tripod at a time, and the step twists the body; the head bobs with the stride. Calm by default: only an ant whose session needs you comes to the middle, grows and waves; a busy one runs a short errand per hook event and otherwise stands; an idle one strolls now and then; a still one creeps along a slow drift (0.35–0.95 pt/s) so nothing burns in. 60 fps while one walks or acts, 30 otherwise. White only. `bench/jeta-ants` measures it.
- The manager session's `jeta:` lines arrive as turn events from every session; `NoticeBoard` reads them and `Screen` decides what shows (question, detail, session list) and what each gesture does. On the bare face a tap pokes it awake and a swipe down opens the session list; with text up a tap opens or closes the detail and a swipe sideways moves between sessions. Holding anywhere is talking (Talk, through che). Two-finger chords still allow or deny. `FaceView.take(_:)` is where the Buddy link feeds events; in the Simulator, launch with `-jeta "jeta: …"` to try a screen. Text moves like the face: `Screen.place` lays the lines out and `TextMotion` gives each one springs, keyed by its words so a line on both screens glides; lines come out of the face after it gets out of their way, a swipe carries the page its way, a chosen option pops and stays lit, and Talk's notes take the hint's place. `bench/jeta-text` counts jumps and text over the face.
- Two or more fingers are a chord, read by JetaKit's `Chord` (after Krenn's car UI): the finger count picks the control, spacing is read once at touch-down, and dragging up or down steps it. One finger never acts; a finger landing late voids the chord. A permission request shows on screen with Allow and Deny, and only a tap on one answers it (a tap anywhere else never decides). Two close fingers with a prompt up also decide: drag up past 120 pt and let go for once, down for deny, short of it sends nothing. Each step clicks and pokes the face, since the SE has no Taptic Engine. A chord decides only while the Buddy core has a prompt a tap could answer, and sends the same decision. `bench/jeta-chord` replays seeded gestures through it.
- The Hardware Buddy link carries no text from device to desktop, so push-to-talk has its own path. `jeta/App/Talk.swift`: hold the face (≥150 ms) to record 16 kHz mono WAV while the face shows `.listening`, release (back to the mood before) to POST it to `che` on the Mac, found over Bonjour (`_che._tcp`, port 8078); a tap in the next 2 s POSTs `/cancel`. `Talk.say(_:to:)` POSTs text (an option picked on the screen) to `/say`, which che types the same way, Enter and `/cancel` included. Both carry `?session=` with the Claude Code session id from the hooks: the face held (or the only one), and for an option the session whose `jeta:` line asked. che finds that session's `local_…` id in the Claude app's `claude-code-sessions` files, opens it with `claude://code/continue?session=…`, and types only once the app's `main.log` says `setFocusedSession` for it; a session the app doesn't have, or one that didn't open in 3 s, leaves the words on the clipboard, never in another window.
- **Hooks over Wi-Fi.** `jeta/hooks on [host]` (JavaScript in osascript, nothing to install) puts hooks in `~/.claude/settings.json` beside the user's own that curl `http://<phone>:8079/hook` with a 1 s connect timeout; the phone is the address `./ya install` saved in `~/.config/yapa/host`, since iOS answers its `claude-yapa.local` name over mDNS only some of the time (a lookup can hang 10 s), and the name only when none is saved, so a phone that's off fails every hook fast. Each ends in `# jeta`, which is how `jeta/hooks off` finds exactly them; the first `on` keeps the file as `settings.json.before-yapa`. Status events run in the background (`async`); `PermissionRequest` waits up to 10 min. The terminal's own dialog shows at the same time and whichever answers first wins; an answer there doesn't end the hook, so the pad lets it go with no decision on the session's next event. jeta's `HookListener` (App/Hooks.swift) takes them from the home network only, BuddyKit's `Desk` keeps every session's state (named by folder) and turns it into the heartbeat the Claude app sends, fed to the same Buddy core; a tap's decision answers the held hook. While any session reports, Bluetooth input is ignored, so the manager's `jeta:` lines come from the hooks too: `Desk.turn` makes a turn event of a Bash `echo` (PreToolUse) and of the text a session stopped on (Stop's `last_assistant_message`). No answer, a timeout or the phone off gives the hook no decision: only a tap approves. `test/jeta-hooks-sim` runs the listener in a booted Simulator.
- `mac/` is the Mac side (SwiftPM, macOS 26+). `TalkKit` holds what tests can reach: WER, language pick, HTTP parsing, routing, the pending Enter, and `Transcriber` (Apple's on-device SpeechTranscriber, en_US and es_ES run in parallel, the more confident wins). `che` types the text with CGEvents into Claude or a terminal in front, else keys it into the Claude app behind without raising it, else leaves it on the clipboard; Enter follows after `CHE_ENTER` s (2). It accepts only this Mac and `CHE_FROM` hosts, IPv4 only. Nothing in the desktop app or `claude` accepts text from outside, short of `claude --channels` with a dev flag, so typing is the one path that reaches both. `mac/install` runs it as a LaunchAgent.
